# 技术设计

## 已知事实与约束

- 项目基于 Dify，首期只在 Dify 内部验证。
- 用户需要英语、越南语、泰语三语交流。
- 首期业务范围包括商品、订单/物流、售后/退款/退换货和知识库管理。
- 人工接管条件是恶劣语气、明确要求人工、连续两次无法回答、退款/赔付/投诉。
- 项目涉及 API/数据结构、新模块、跨模块行为规则，且需求不确定性较高。
- 首期不接入外部渠道，不执行自动退款或赔付。

## 目标与非目标

- **目标**：在 Dify 中验证分层客服流程、三语回复、知识库生命周期和人工接管；常见问题回答准确率达到 90%。
- **非目标**：外部渠道接入、自动翻译专项优化、客服数据分析、自动执行退款/赔付。

## 决策（Decisions）

### 决策：采用分层工作流

- **选择**：按语言识别、意图路由、知识检索、业务回答、风险判断和人工接管拆分节点/分支。
- **理由**：可独立验证三语处理、业务边界和转人工规则，减少单一提示词覆盖所有场景造成的不可控行为。
- **替代方案**：单一工作流开发更快但容易形成难维护的长流程；自主 Agent 更灵活但难以保证高风险场景稳定转人工。
- **后果**：初期配置和测试成本更高，但后续接入订单系统、外部渠道或数据分析时可以沿用路由边界。

### 决策：知识库采用版本和生效控制

- **选择**：只有已生效版本参与检索，测试结果展示文档来源和版本。
- **理由**：跨境客服内容会更新，回答必须能够追溯依据并避免停用内容继续生效。
- **替代方案**：直接覆盖文档简单，但无法回溯错误回答的依据，也无法安全验证新版本。
- **后果**：需要维护版本状态和文档元数据；首期需准备覆盖三类业务的基准文档。

### 决策：高风险场景优先人工接管

- **选择**：退款、赔付、投诉、恶劣语气、明确转人工和连续两次无法回答均转人工。
- **理由**：降低错误承诺、情绪升级和财务/投诉风险，符合首期先验证客服分流而非自动执行交易的目标。
- **替代方案**：让机器人继续尝试回答可以提高自动化比例，但会扩大误答和投诉风险。
- **后果**：需要生成会话摘要和转人工状态；自动化率可能低于无门槛 Agent，但结果更可控。

## 风险与验证

- **三语识别或表达不准确** → 为每种语言准备等价测试样例 → 运行三语意图和回答测试集并分别统计结果。
- **知识库版本混用** → 强制生效状态过滤并展示来源版本 → 用旧版/新版/停用版文档执行检索测试。
- **转人工规则漏判** → 将规则作为独立风险判断分支 → 对四类触发条件和连续失败计数执行回归测试。
- **准确率目标无法复现** → 固定问题、期望意图、期望回答要点和转人工结果 → 在 Dify 预览中重复运行同一验收集并保存结果。
